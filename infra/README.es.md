# Infraestructura de desarrollo local

El `docker-compose.yml` de la raíz ejecuta la web pública, el backoffice y `services/api`, con inventario en PostgreSQL de Supabase. Configura `.env` en la raíz y `services/api/.env` según el README principal y arranca con `docker compose up`; usa `docker compose up --build` después de cambiar un Dockerfile o un archivo de bloqueo de dependencias. Si falta `SUPABASE_DATABASE_URL` en el `.env` de la raíz o está vacía, Compose se detiene antes de arrancar.

Los Dockerfiles viven junto al código que contienen: `uis/Dockerfile` construye la imagen Node Alpine y `services/Dockerfile` construye la API Python. `uis/start.sh` arranca website y backoffice en un solo contenedor. Cada contexto tiene su propio `.dockerignore`; las carpetas de código se montan para permitir recarga en caliente y los datos usan volúmenes nombrados.

En Docker Desktop, las interfaces usan Webpack con polling cada segundo (`NEXT_DOCKER_POLLING=1`) porque el montaje de archivos de Windows puede retrasar eventos del sistema. Es un ajuste solo de Compose; añade algo de actividad de CPU y disco. En desarrollo fuera de Docker, Next mantiene su configuración normal.

La API carga `.env.example`, el `.env` obligatorio de la raíz y después el `services/api/.env` obligatorio. Compose selecciona explícitamente `SUPABASE_DATABASE_URL` de la raíz, fija las rutas de persistencia del contenedor y desactiva dotenv. Los secretos de autenticación y las credenciales del administrador inicial proceden de `services/api/.env`; el ejemplo de la raíz no incluye una contraseña de desarrollo compartida. Los `.env` reales se excluyen de los contextos de construcción y la API mantiene su `.env` montado enmascarado con el ejemplo seguro.

El montaje existente del código del backend comparte también `services/api/data/users.json`: Docker y la ejecución local usan las mismas cuentas, perfiles, hashes de contraseña y UUID. Solo para un almacén nuevo, ejecuta `docker compose exec api uv run --no-sync seed-users`. Los proveedores conservan el volumen `api_data`; Next.js conserva sus volúmenes de caché. La API instala las versiones fijadas en `services/api/requirements.txt`, exportadas desde `uv.lock`.

El backoffice envía las llamadas del navegador a la API mediante un proxy de Next.js hacia el servicio Compose `api`. La API utiliza la URL de Supabase con `sslmode=require`; los contenedores comparten la red con nombre `nexova-local`. Compose ya no define un servicio ni un volumen PostgreSQL local. Los volúmenes PostgreSQL existentes no se borran ni se migran; el contenedor PostgreSQL anterior puede detenerse por separado. Los puertos de desarrollo son 3000 (website), 3001 (backoffice) y 8000 (API). Tras cambiar variables de entorno, recrea la API con `docker compose up -d --no-deps --force-recreate api`.
